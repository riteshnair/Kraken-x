# Exact RV32/tensor coprocessor

`krk::Rv32` is an optional, host-side compute coprocessor in `krk_core`. It
provides exact integer arithmetic and control flow, byte-addressed memory, and
Qwenputer-compatible `WB`, `VDOT`, and `SMAQA` tensor instructions.

It is **not** an in-weight CPU. Qwenputer's transformer implementation uses
compiled circuit layers in a specialized checkpoint; adding this interpreter
does not add those circuits to an ordinary GGUF. It also does not run implicitly
in transformer forward passes. Model routing, sampling, expert selection,
expert-cache residency, and generated output are unchanged unless a caller
explicitly invokes this API or the `kraken-rv32` tool.

## ISA and execution model

- RV32I, M, and the `SH1ADD`/`SH2ADD`/`SH3ADD` portion of Zba.
- Naturally aligned `LB/LH/LW/LBU/LHU` and `SB/SH/SW` with checked addresses.
- Exact signed division overflow and division-by-zero behavior.
- Pure reads of the Qwenputer CSR stubs; CSR writes and unsupported operations
  fault instead of being silently ignored.
- `ecall` with `a7=1` appends the low byte of `a0` to output; `a7=93` exits.
- A configurable instruction limit and explicit fault type/PC. Faulting
  instructions do not commit architectural changes.
- Optional per-instruction commit records. Trace and state hashes are produced
  even when trace retention is disabled, so enabling traces cannot change
  execution.

Memory belongs to an `Rv32` instance and remains available across `run()` calls.
`reset()` clears byte RAM, registers, output, and execution state while retaining
installed tensor codes. `read_bytes()` and `store_bytes()` allow a host to save
and restore memory. Tensor weights are separate from byte RAM and immutable to
firmware stores.

## Tensor compatibility

Custom opcode `0x0b`, `funct7=0` uses:

| Instruction | `funct3` | Operation |
| --- | ---: | --- |
| `VDOT rd,rs1,rs2` | 5 | Accumulate eight signed activation bytes times eight signed int4 weights into `rd` |
| `WB rs1` | 6 | Set the PC-relative weight-word base |
| `SMAQA rd,rs1,rs2` | 7 | Accumulate four signed-byte products into `rd` |

Tensor codes are supplied as one byte per cell. Only the low nibble is used and
its signed value is `code - 8`; missing cells have code zero. As in Qwenputer's
`npu` reference, the weight PC is `(WB_delta + instruction_PC/4) mod 32768` and
addresses one eight-cell word. `WB` at PC word `w` sets
`WB_delta = (rs1 - w - 1) mod 32768`. Consequently, intervening instructions
advance the weight PC; VDOT is not merely a streaming cursor.

The older Qwenputer decimal digit-file custom instructions (`funct3` 0–4) and
`BPRD` are not part of this tensor-focused implementation and fault as illegal.

## API

Include `krk/rv32.hpp`, construct `krk::Rv32`, load a flat binary with `load()`,
optionally install tensor codes with `set_tensor_weights()`, and call `run()`.
The object is single-threaded; use separate instances for concurrent jobs.

```cpp
krk::Rv32 machine(64 * 1024);
machine.load(0, program_bytes, program_size);
machine.set_tensor_weights(std::move(int4_codes));
if (!machine.run(1'000'000)) {
    // Inspect machine.fault(), machine.fault_pc(), and machine.trace().
}
```

## Flat-binary runner

```sh
cmake --build build-cpu --target kraken-rv32 kraken-rv32-tests
./build-cpu/kraken-rv32-tests
./build-cpu/kraken-rv32 program.bin --max-steps 1000000 --trace commit.tsv
```

`program.bin` is a raw, 32-bit little-endian instruction image, not an ELF. Use
`--entry` to select its load/entry address and `--weights` for a separate tensor
code file. Output bytes go to stdout; the result, instruction count, fault PC,
and deterministic hashes go to stderr. Trace TSV contains committed register and
memory transitions.

## Correctness and performance boundary

`tools/ta_rv32.cpp` checks arithmetic, division corners, memory, branches,
output, faults, tracing equivalence, and Qwenputer tensor addressing, plus 256
deterministic tensor programs against independent arithmetic. Run it through
`ctest -R kraken-rv32`.

The implementation favors auditability over host emulation throughput. Scalar
emulation is not inherently faster than direct native arithmetic or Kraken's
existing GEMM/vector backends. No inference or tensor speedup is claimed.
Any future automatic backend offload must preserve bit-exact results and pass a
separate latency/throughput measurement gate. Expert-cache prefetch and residency
remain advisory: physical cache state must never change logical expert routing
or reduction order.
